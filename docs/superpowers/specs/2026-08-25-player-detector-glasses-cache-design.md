# 玩家实例级探测眼镜缓存设计

## 问题

`EntityInvisibleMixin` 当前使用玩家 UUID 作为键，分别在两个静态 `ConcurrentHashMap` 中保存探测眼镜结果和对应的 `tickCount`。客户端玩家、服务端玩家以及重生前后的玩家对象可能具有相同 UUID 和相同 tick，但其装备或 Curios 同步状态并不一定一致。缓存因此可能在不同玩家实例或逻辑线程之间串用。

两张独立 Map 还会增加每次命中的哈希查询成本，并需要额外的在线玩家清理逻辑。

## 目标

- 同一玩家实例在同一 tick 最多扫描一次装备和 Curios。
- 客户端、服务端及重生后的玩家实例完全隔离。
- 移除 UUID 缓存、并发 Map 和手动清理。
- 不改变探测眼镜的有效槽位、揭示范围或配置行为。
- 保持同 tick 内装备变化最迟在下一 tick 生效的现有语义。

## 设计

新增一个仅暴露“读取本实例探测眼镜状态”方法的接口，以及一个以 `Player` 为目标的 Mixin。Mixin 为每个玩家实例注入：

- 一个上次扫描的 tick，初始值使用不可能与正常初始 tick 命中的哨兵值；
- 一个上次扫描得到的布尔结果。

接口方法比较玩家当前 `tickCount` 与缓存 tick。不同则调用现有 `CurioCompat.hasItemInCurioOrSlot` 扫描装备和兼容的 Curios 槽，按“先写结果、后发布 tick”的顺序更新字段；相同则直接返回布尔字段。

`EntityInvisibleMixin` 将玩家转换为该接口并读取状态。原来的 UUID、结果 Map、tick Map 以及在线玩家清理代码全部删除。探测眼镜物品仍通过注册表缓存取得。

该玩家 Mixin 只增加字段和接口方法，不注入、覆盖或重定向 `Player` 的现有方法，减少与其他模组的冲突面。

## 运行语义

- 客户端和服务端拥有不同的玩家对象，因此各自保存缓存，不会因 UUID 相同而互相复用。
- 死亡重生会创建新玩家对象，新对象从无效缓存状态开始；旧对象及字段随对象回收。
- 切换维度若保留同一玩家对象，则装备状态不变时继续按 tick 刷新；若替换对象，则自动得到独立缓存。
- 同一 tick 中首次查询执行实际扫描，后续查询只进行实例方法调用、整数比较和布尔读取。

## 明确不做

不与 `DetectorGlowState` 合并。`CurioCompat.hasItemInCurioOrSlot` 只承认装备槽和与物品兼容的 Curios 槽，而发光开关当前会检查所有装有该物品的 Curios 槽。合并扫描会改变现有槽位语义并复制上游 Curios 过滤规则，不属于本次缺陷修复。
